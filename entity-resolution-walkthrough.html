1 · What we're building

By the end of this walkthrough, you'll understand exactly how Syngage assembles this kind of sentence from public data:

The output — one composed BD-ready sentence Moderna (MRNA · CIK 1682852) has 47 recruiting trials on CT.gov, got a Priority NDA supplement accepted last month via openFDA, raised $500M via 424B on EDGAR three weeks ago, and hasn't announced a commercial CDMO in any 8-K. Engage now.

Every clause in that sentence comes from a different public data source. The magic is joining them into one story about one company. That "joining" is what we call entity resolution.

Why it matters: Any competitor (Salesmotion, Zymewire, ZoomInfo) can query one data source and fire an alert. Syngage's differentiator is combining three data sources into a value-chain-aware partnership rationale. The join is the moat.

3 · The problem — why we can't just query

Each source has its own way of identifying a company. To combine data, we need one identifier that works everywhere.

SourceIdentifies companies byExample (for Moderna)
CT.govFree-text sponsor name"Moderna, Inc." · "ModernaTX" · "MODERNA" (any variant)
openFDAFree-text sponsor name (uppercase convention)"MODERNA" · "MODERNATX INC"
SEC EDGARNumeric CIK (Central Index Key)1682852
Stock marketTicker symbolMRNA
The chain we need: messy sponsor name → normalized name → ticker → CIK. Once we have the CIK, we can query SEC. Once we can join CT.gov + openFDA + SEC by CIK, we have the combined story.

4 · Pipeline overview

Nine steps total. Steps 1-4 are entity resolution. Steps 5-8 are parallel API queries, each contributing one clause to the sentence. Step 9 composes them.

1
Start with a messy sponsor name
Input: a trial from CT.gov · Output: a raw sponsor name string
Entity resolution

The pipeline starts because someone (or a scheduled job) noticed an interesting trial on CT.gov. Every trial record has a leadSponsor.name field — free text entered by whoever registered the trial. That's our starting point.

Example CT.gov call 
GET https://clinicaltrials.gov/api/v2/studies/NCT04470427?format=json
Response — just the fields we care about right now
{
  "protocolSection": {
    "identificationModule": {
      "nctId": "NCT04470427",
      "briefTitle": "A Study to Evaluate the Immunogenicity..."
    },
    "sponsorCollaboratorsModule": {
      "leadSponsor": {
        "name": "ModernaTX, Inc.",
        "class": "INDUSTRY"
      }
    }
  }
}
Input
NCT04470427
→
Output
"ModernaTX, Inc."
Gotcha: The same real company appears under many name variants across trials — "ModernaTX, Inc.", "Moderna, Inc.", "MODERNA", "Moderna Therapeutics", subsidiaries like "Moderna Biotech Spain". You cannot use this raw name as a database key.
2
Normalize the name
Input: messy string · Output: cleaner string for matching
Entity resolution

Basic string cleanup so that "ModernaTX, Inc." and "MODERNA THERAPEUTICS, INC." both reduce to the same normalized form. This step happens in code — no API call needed.

Pseudocode 
function normalize(name) {
  return name
    .toLowerCase()
    .replace(/,?\s*(inc|corp|ltd|llc|plc|co|corporation|therapeutics|
              pharmaceuticals|biotech|holdings)\.?/g, "")
    .replace(/[^a-z0-9\s]/g, "")
    .replace(/\s+/g, " ")
    .trim();
}
Input
"ModernaTX, Inc."
→
Output
"modernatx"
Tip: Normalization is domain-specific. For biotech, always strip corporate suffixes (Inc, Corp, LLC, PLC) AND industry noise words (Therapeutics, Pharmaceuticals, Biotech, Holdings). Keep the distinguishing tokens.
3
Match normalized name → ticker
Input: normalized name · Output: stock ticker (or "private, no ticker")
Entity resolution

The hardest step. Given "modernatx", figure out that the stock ticker is MRNA. Three options ranked from best to worst:

Option A · LLM lookup (recommended)

Ask a fast, cheap LLM (Haiku, GPT-4o-mini) to map the name. Works well because LLMs know common biotech tickers from training data.

Prompt to Haiku (or similar) 
Given this company name, return only the US stock ticker if it's public,
or "PRIVATE" if not.

Name: modernatx
Ticker:
LLM response
MRNA

Option B · Fuzzy match against company_tickers.json titles

The tickers file (see Step 4) has a title field per row. Do a fuzzy string match ("modernatx" vs each normalized title). Slower but no LLM cost.

Option C · Human-in-the-loop review UI

When confidence is low (multiple candidates, or none), queue the match for manual review. The V2 doc explicitly recommends this for the tricky 20%.

Input
"modernatx"
→
Output
"MRNA"
Gotcha: Not every sponsor has a ticker. Private biotechs and stealth-mode startups have no public identifier at all — you can't resolve them to a CIK. That's OK. The pipeline just skips SEC data for those and works with CT.gov + openFDA only.
4
Ticker → CIK via company_tickers.json
Input: ticker · Output: 10-digit CIK
Entity resolution

The SEC publishes a single JSON file listing every ticker → CIK mapping. Download it once (or refresh weekly — it changes slowly), then look up locally in O(1).

One-time download (via Syngage backend proxy — SEC requires User-Agent) 
GET https://www.sec.gov/files/company_tickers.json
Headers: User-Agent: Syngage AI ops@syngage.ai
Structure of the file — ~10,000 rows
{
  "0":    {"cik_str": 320193, "ticker": "AAPL",  "title": "Apple Inc."},
  "1":    {"cik_str": 789019, "ticker": "MSFT",  "title": "MICROSOFT CORP"},
  ...
  "3891": {"cik_str": 1682852, "ticker": "MRNA", "title": "Moderna, Inc."},
  ...
}
Lookup in code (in-memory index) 
const tickerIndex = buildIndex(companyTickers);  // ticker → row
const cik = tickerIndex["MRNA"].cik_str;          // 1682852
const cikPadded = String(cik).padStart(10, "0");  // "0001682852"
Input
"MRNA"
→
Output
"0001682852"
Now we have the join key. That 10-digit CIK is what every downstream SEC query needs. Steps 5-8 use it (or the sponsor name where SEC isn't involved) to fetch four different pieces of the story in parallel.
5
Query CT.gov for recruiting trial count
Contributes clause: "has 47 recruiting trials on CT.gov"
CT.gov

      &countTotal=true
      &pageSize=0
Response — we only need one field
{
  "totalCount": 47,
  "studies": [],
  "nextPageToken": null
}
Input
Sponsor name: "Moderna"
→
Output
47

6
Query openFDA for Priority NDA submissions
Contributes clause: "got a Priority NDA supplement accepted last month via openFDA"
openFDA

Has this sponsor filed anything with FDA under Priority review recently? Priority review = 6-month clock instead of 10-month = commercial launch approaching soon = CDMO scale-up conversation window.

Query — Elasticsearch-style syntax 
GET https://api.fda.gov/drug/drugsfda.json
      ?search=sponsor_name:"MODERNA"
        +AND+submissions.review_priority:"PRIORITY"
        +AND+submissions.submission_status_date:[20260601+TO+20260701]
      &limit=5
Response — abbreviated to the relevant fields
{
  "results": [{
    "application_number": "BLA125752",
    "sponsor_name": "MODERNATX INC",
    "submissions": [
      {
        "submission_type": "SUPPL",
        "submission_number": "5",
        "submission_status": "AP",
        "submission_status_date": "20260615",
        "review_priority": "PRIORITY"
      }
    ],
    "products": [{"brand_name": "SPIKEVAX", "generic_name": "..."}]
  }]
}
Input
Sponsor: "MODERNA" · Date range: last 30 days
→
Output
Priority SUPPL, approved 2026-06-15
Gotcha: openFDA sponsor names are usually UPPERCASE and often omit corporate suffixes ("MODERNATX INC" not "ModernaTX, Inc."). Do the same name normalization from Step 2 before matching.

7
Query EDGAR for recent financings
Contributes clause: "raised $500M via 424B on EDGAR three weeks ago"
SEC EDGAR

Did this sponsor raise capital recently? A 424B filing (or S-1) means they just issued stock and got cash. That confirms they have budget to spend on CDMOs / CROs.

Query — uses the CIK from Step 4 
GET https://data.sec.gov/submissions/CIK0001682852.json
Headers: User-Agent: Syngage AI ops@syngage.ai
Response — recent filings section, filtered for 424B*
{
  "cik": "1682852",
  "name": "Moderna, Inc.",
  "tickers": ["MRNA"],
  "filings": {
    "recent": {
      "form":               ["10-Q", "8-K", "424B5", "8-K", ...],
      "filingDate":         ["2026-06-30", "2026-06-25", "2026-06-20", ...],
      "accessionNumber":    ["...", "...", "0001193125-26-158000", ...],
      "primaryDocument":    ["...", "...", "d123456d424b5.htm", ...]
    }
  }
}
Note the two-step nature: the submissions API tells us a 424B was filed on 2026-06-20. But the $500M dollar amount lives inside the actual 424B document (an HTML/PDF filing), not in the JSON. To extract it we'd fetch the primary document URL and regex or NLP for phrases like "offering size" or "gross proceeds".
Input
CIK: 0001682852
→
Output
424B5 filed 2026-06-20 ($500M — from doc)
8
Query EDGAR full-text for CDMO announcements
Contributes clause: "hasn't announced a commercial CDMO in any 8-K"
SEC EDGAR

Critical negative signal: has this sponsor already announced a commercial manufacturing partner? If yes, that slot is taken and we shouldn't pitch a competitor. If no, the slot is open — engage.

Full-text search across all 8-Ks for this CIK 
GET https://efts.sec.gov/LATEST/search-index
      ?q="commercial+supply+agreement"+OR+"manufacturing+agreement"
        +OR+"contract+manufacturer"
      &forms=8-K
      &ciks=0001682852
Response — we want the total count
{
  "hits": {
    "total": {
      "value": 0,       // ← zero hits = no CDMO announcement = open slot
      "relation": "eq"
    },
    "hits": []
  }
}
Input
CIK: 0001682852 · Keywords: manufacturing/supply
→
Output
0 hits · no CDMO announced
Gotcha: Keyword coverage matters. Sponsors describe the same relationship in many ways: "commercial supply agreement", "manufacturing agreement", "contract manufacturer", "commercial CDMO", "manufacturing partner", "toll manufacturing". OR all common phrasings — a false negative here becomes a wasted BD outreach.
9
Compose the sentence
Input: 4 API responses joined by CIK · Output: one BD-ready sentence
Reasoning layer

A tiny template stitches the four responses into a single sentence. No further API calls — this is all in code.

Pseudocode template 
const parts = await Promise.all([
  fetchCTgov(sponsor),                    // → {totalCount: 47}
  fetchOpenFDA(sponsor),                  // → {results: [{...priority NDA...}]}
  fetchEdgarSubmissions(cik),             // → {filings: {...424B5...}}
  fetchEdgarSearch(cik, cdmoKeywords)     // → {hits: {total: {value: 0}}}
]);

const sentence = `
${company.name} (${company.ticker} · CIK ${company.cik}) has
${parts[0].totalCount} recruiting trials on CT.gov,
${parts[1].results.length > 0
    ? 'got a ' + parts[1].results[0].submissions[0].review_priority + ' NDA supplement accepted ' + relativeTime(parts[1].results[0].submissions[0].submission_status_date)
    : 'has no recent Priority submissions'} via openFDA,
${latest424B(parts[2])
    ? 'raised ' + extractOfferingSize(latest424B(parts[2])) + ' via 424B on EDGAR ' + relativeTime(latest424B(parts[2]).filingDate)
    : 'has no recent financing activity'},
${parts[3].hits.total.value === 0
    ? "and hasn't announced a commercial CDMO in any 8-K. Engage now."
    : 'and has an existing manufacturing partner. Monitor.'}
`;
Assembled output Moderna (MRNA · CIK 1682852) has 47 recruiting trials on CT.gov, got a Priority NDA supplement accepted last month via openFDA, raised $500M via 424B on EDGAR three weeks ago, and hasn't announced a commercial CDMO in any 8-K. Engage now.
That's it. Four parallel API calls, joined by one identifier (CIK), stitched by one template. No AI in the composition itself — the reasoning is baked into the query design and the template branching. This is exactly what the V2 doc calls the "signal → value-chain-partner catalog".

6 · Glossary

CIK · Central Index Key
The SEC's permanent unique ID for every entity that files with them. 10 digits, zero-padded. Never changes. The join key that makes the whole pipeline work.
Ticker
Stock exchange short code (1-5 letters). Not permanent — companies can change tickers or delist. Useful as an intermediate step because it's more memorable than a CIK.
NCT ID
ClinicalTrials.gov's unique trial identifier. Format: "NCT" + 8 digits.
NDA / BLA / ANDA
FDA drug application types. NDA = New Drug Application (small molecule). BLA = Biologics License Application (biologic). ANDA = Abbreviated New Drug Application (generic).
PDUFA date
The FDA's promised decision deadline for a drug application. Standard review = 10 months, Priority review = 6 months. No official API — must be mined from 8-K text.
Priority review
FDA designation that shortens the review clock from 10 months to 6 months. Signals a launch is soon → CDMO commercial-scale conversation window.
8-K
SEC "material events" filing. Companies file one within 4 business days of any big news: partnerships, financings, PDUFA dates, executive changes. Highest-signal filing type.
10-K / 10-Q
Annual / quarterly financial reports. Contain revenue, R&D spend, cash position, business overview.
S-1 / 424B
Securities offering filings. S-1 = registration statement for a new offering (IPO or secondary). 424B = the final prospectus with pricing and offering size.
CDMO · Contract Development and Manufacturing Organization
Company that manufactures drugs on behalf of a sponsor. The classic Syngage prospect.
CRO · Contract Research Organization
Company that runs clinical trials on behalf of a sponsor. Also a classic Syngage prospect.
Entity resolution
The pipeline that maps a messy real-world identifier (sponsor name in free text) to a canonical database key (CIK, ticker). The moat.
Fair Access (SEC)
SEC's policy requiring all API clients to include a User-Agent header identifying the requester. Enforced with a 10 req/s rate limit per IP. Browsers can't set User-Agent, so you need a backend proxy.
