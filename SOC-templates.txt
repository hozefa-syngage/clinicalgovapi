1. PURPOSE

This policy establishes Syngage AI's commitment to protecting:
  • Customer data (clinical trial information, pharmaceutical research)
  • Intellectual property (algorithms, proprietary models)
  • Employee information (personally identifiable information)
  • Systems and infrastructure from unauthorized access, use, or disclosure

All employees, contractors, and third-party vendors must comply with this
policy to maintain customer trust and regulatory compliance.


2. SCOPE

This policy applies to:
  ✓ All full-time and part-time employees
  ✓ Independent contractors and consultants
  ✓ Third-party vendors with system access
  ✓ All company systems (cloud platforms, databases, laptops, mobile devices)
  ✓ All data handling (customer data, financial information, proprietary IP)

Exclusions:
  ✗ Personal devices used only for email/Slack (covered under BYOD section)
  ✗ Physical office security (managed by landlord/facilities)

This policy is based on:
  • NIST Cybersecurity Framework (core functions: Identify, Protect, Detect, Respond, Recover)
  • SOC 2 Trust Services Criteria (Common Criteria 1-9)

5. DATA CLASSIFICATION LEVELS

All data at Syngage AI falls into one of four categories:


5.1 PUBLIC DATA
Definition: Data safe for public consumption without restriction
Examples:
  • Marketing blog posts
  • Published case studies (with customer approval)
  • Press releases
  • Publicly available documentation

Handling Requirements:
  • No special access controls
  • No encryption required
  • Can be shared publicly without approval

Retention:
  • Keep indefinitely or per business need


5.2 INTERNAL DATA
Definition: Non-sensitive business information for internal use only
Examples:
  • Meeting notes (non-confidential)
  • Organizational charts
  • Internal announcements
  • Project plans (non-proprietary)
  • General business metrics

Access:
  • Employees only
  • No external sharing without approval

Handling Requirements:
  • Store in company systems only (no personal email)
  • No printing sensitive internal data
  • Secure deletion when no longer needed

Retention:
  • 3 years minimum (for audit trail)
  • Then delete securely


5.3 CONFIDENTIAL DATA
Definition: Business-sensitive information with risk if disclosed
Examples:
  • Customer data (company names, trial information)
  • Financial information (revenue, costs, contracts)
  • Intellectual property (algorithms, models)
  • Pricing and proposals
  • Vendor contracts

Access:
  • Need-to-know basis only
  • Department heads approve access
  • Documented access log maintained

Handling Requirements:
  • Encrypted at rest (all systems must use encryption)
  • Encrypted in transit (HTTPS/TLS 1.2 minimum)
  • No storage on personal devices (see BYOD policy below)
  • No screenshots without [REDACTED] labels
  • No forwarding to personal email accounts

Retention:
  • Per customer contract (typically 7 years for audit purposes)
  • Then securely delete


5.4 RESTRICTED DATA
Definition: Highly sensitive credentials and authentication materials
Examples:
  • API keys and secrets (OpenAI, Claude, Supabase)
  • Database passwords
  • AWS/Cloud platform credentials
  • SSH private keys
  • MFA backup codes
  • Personal identification numbers (PII if collected)

Access:
  • Only assigned individuals (explicitly authorized by CISO)
  • No sharing via email or Slack
  • No written on whiteboards or paper

Handling Requirements:
  • Stored ONLY in encrypted vault (1Password, Bitwarden, or equivalent)
  • Never in code repositories (use environment variables)
  • Never in Slack or email
  • Rotate on any suspected compromise
  • Immediate revocation upon employee termination

Retention:
  • Delete immediately when no longer needed
  • Rotate credentials every 90 days


6. DATA HANDLING RULES

6.1 General Rules
  ✓ All data encrypted at rest (databases, file storage)
  ✓ All data encrypted in transit (TLS 1.2+ minimum)
  ✓ Access logged (who accessed what data, when)
  ✓ Data backups created daily (retention: 30 days minimum)
  ✓ Backups tested for recovery (monthly restore drills)

6.2 Customer Data
  ✓ Only access if required for job function
  ✓ Process via company systems only
  ✓ No exporting to personal files
  ✓ No sharing with unauthorized colleagues
  ✓ Immediate reporting if unauthorized access suspected

6.3 Personal Devices (BYOD)
  ✗ FORBIDDEN: Accessing customer data on personal laptops/tablets
  ✗ FORBIDDEN: Viewing production logs on personal phone
  ✗ FORBIDDEN: Checking API credentials on personal device
  ✗ FORBIDDEN: Screenshots of customer data on personal devices

  ✓ ALLOWED: Email and Slack (read-only, no data export)
  ✓ ALLOWED: Public documentation

  Violation Consequences:
  • First violation: Verbal warning + security retraining
  • Repeat violation: Written warning + possible access revocation
  • Severe/intentional violation: Termination

6.4 Data Destruction
When data is no longer needed (RESTRICTED/CONFIDENTIAL only):
  • Secure deletion (not just trash/recycle bin)
  • Use built-in OS secure delete or encrypted-disk wipe
  • For drives: Full-disk encryption wipe
  • For backups: Confirmed deletion after retention period

6.5 Third-Party Data Processors
Any vendor processing customer data must:
  ✓ Sign Data Processing Agreement (DPA)
  ✓ Maintain same encryption standards as Syngage
  ✓ Undergo annual security assessment
  ✓ Report breaches within 24 hours

7. DEFINITION OF A SECURITY INCIDENT

Any of the following constitutes a security incident:
  • Unauthorized access to company systems or customer data
  • Data breach (customer information exposed)
  • Malware or ransomware infection
  • Compromised credentials or credentials accessed
  • DDoS or other cyber attack
  • Phishing emails with successful compromise
  • Accidental disclosure of confidential information
  • System outage due to security failure (not just infrastructure)
  • Insider threat (malicious employee activity)


8. INCIDENT RESPONSE PROCEDURE

All incidents follow this 5-step process:

STEP 1: DISCOVER & REPORT (Within 15 minutes)
  Action: Any employee who discovers an incident must report immediately
  To: Email security@syngage.ai OR call [CISO PHONE NUMBER]
  Include:
    • What happened (describe the issue)
    • When discovered (date/time)
    • Where detected (system/application)
    • Who's affected (customers, employees, systems)

  DO NOT:
    ✗ Delete evidence or logs
    ✗ Restart affected systems
    ✗ Attempt to "fix it yourself"
    ✗ Post about it on Slack/email before CISO notified


STEP 2: TRIAGE & INITIAL RESPONSE (Within 1 hour)
  CISO Actions:
    • Assess severity (Critical, High, Medium, Low)
    • Notify CEO immediately if Critical
    • Form incident response team
    • Preserve evidence (don't overwrite logs)
    • Contain the threat (if needed)

  Severity Levels:
    CRITICAL: Customer data exposed, system down, regulatory breach
      → Notify CEO + Board within 1 hour
      → Activate 24/7 response team
      → Customer notification within 24 hours

    HIGH: Suspected breach, unauthorized access, credential compromise
      → Notify VP Eng + CEO within 2 hours
      → Full investigation within 24 hours
      → Potential customer notification within 72 hours

    MEDIUM: Suspicious activity, potential vulnerability, failed access attempt
      → Notify VP Eng within 4 hours
      → Investigation within 5 business days
      → No immediate customer notification (unless breach confirmed)

    LOW: Minor security event, no data impact, false alarm
      → Log in incident tracker
      → Review for patterns


STEP 3: INVESTIGATION (Within 5 business days)
  Investigation Team:
    • CISO (lead)
    • VP Engineering
    • Relevant engineer (system involved)
    • Legal counsel (if breach suspected)

  Investigation Goals:
    • What happened? (Technical analysis)
    • When did it start? (Timeline)
    • Who caused it? (Accidental vs intentional)
    • How much data affected? (Scope)
    • Why was it possible? (Root cause)

  Evidence Preservation:
    • Collect system logs (7+ days)
    • Database access logs
    • Application logs
    • Employee email if involved
    • Store in secure, read-only location

  Timeline Documentation:
    • Hour-by-hour log of actions taken
    • Decisions made and by whom
    • Communications with staff/customers


STEP 4: REMEDIATION & NOTIFICATION (Within 72 hours)

  If No Breach Confirmed:
    ✓ Fix underlying vulnerability
    ✓ Deploy patch or workaround
    ✓ Test thoroughly before deploying
    ✓ Notify CEO of resolution
    ✓ No customer notification required

  If Breach Confirmed (Customer Data Exposed):
    ✓ Determine affected customer(s)
    ✓ Prepare customer notification email
    ✓ Include: What happened, what data affected, when, what we're doing
    ✓ Notify within 24-72 hours (regulatory requirement - GDPR/CCPA)
    ✓ Offer free credit monitoring if PII affected
    ✓ Provide incident report (detailed + redacted versions)
    ✓ Notify regulators if required (attorney guidance)


STEP 5: POST-INCIDENT REVIEW (Within 10 business days)

  Blameless Postmortem:
    • What happened? (Timeline)
    • Why was it possible? (Root cause, not "someone made a mistake")
    • How do we prevent it? (Process/technology improvements)
    • Who will implement fixes? (Owners + deadlines)

  Actions:
    • Update Security Policy if needed
    • Enhance monitoring/detection
    • Conduct staff training on related risks
    • Update Incident Response Plan based on learnings
    • File incident report (for auditors)

  Documentation:
    • Incident report saved to secure folder
    • Action items tracked in Security Committee
    • Evidence archived (3 years minimum)


9. BREACH NOTIFICATION TIMELINES

Regulation:
  • GDPR (EU customer data): Notify within 72 hours of discovery
  • CCPA (California): Notify within 30 days (or "without unreasonable delay")
  • HIPAA (if healthcare): Notify within 60 days (rare for Syngage)

Company Standard:
  • Critical: 24 hours
  • High: 72 hours
  • Medium: As investigation proceeds


10. INCIDENT LOGGING & AUDIT TRAIL

All incidents are logged in Incident Register:

  Fields Tracked:
    • Date discovered
    • Incident type (breach/attack/compromise/accident)
    • Severity (Critical/High/Medium/Low)
    • Systems affected
    • Data affected (customer/employee/IP)
    • Root cause
    • Remediation steps
    • Timeline to resolution
    • Cost (if any)
    • Lessons learned

  Retention:
    • Keep minimum 3 years (for auditors)
    • Share with external auditors during SOC 2

11. COMPANY ASSET MANAGEMENT

All company-owned devices are company property and subject to monitoring.


11.1 LAPTOPS / DESKTOPS

Security Controls:
  ✓ Full-disk encryption mandatory (BitLocker on Windows, FileVault on Mac)
  ✓ Antivirus/EDR software installed (e.g., Defender or CrowdStrike)
  ✓ Auto-lock after 5 minutes of inactivity (must have password to wake)
  ✓ Password required (see password policy below)
  ✓ Windows/macOS updates installed automatically
  ✓ Firewall enabled
  ✓ SSH keys for engineers stored in secure vault (not in ~/.ssh with default permissions)

Software:
  ✓ Only company-approved applications
  ✓ No unauthorized personal software
  ✓ No screen-sharing applications (Zoom only)
  ✓ No personal cloud storage (OneDrive, Dropbox, Google Drive for personal use)

Monitoring:
  • Login/logout tracked
  • Failed login attempts logged
  • Software installation logged
  • Removed upon termination (all accounts wiped)

Lost or Stolen Device:
  1. Report to IT immediately
  2. CISO disables remote access
  3. For encrypted device: Assume data secure (encryption prevents access)
  4. For non-encrypted device: Report as potential breach
  5. File police report
  6. Notify customers if data breach suspected
  7. Replace device


11.2 MOBILE DEVICES (SMARTPHONES/TABLETS)

Policy:
  ✓ Company-issued devices enrolled in Mobile Device Management (MDM)
  ✓ MFA required for any company app access
  ✓ Auto-lock after 5 minutes inactivity
  ✓ Antivirus app installed

Approved for:
  ✓ Email and Slack (read-only)
  ✓ Company chat
  ✗ NO customer data access
  ✗ NO production logs/dashboards
  ✗ NO API credentials

Termination:
  • IT performs remote MDM wipe (all data deleted) on day of separation
  • No manual return needed (data destroyed remotely)


11.3 BYOD (BRING YOUR OWN DEVICE) POLICY

Personal devices are NOT permitted for any company work involving customer data.

STRICTLY PROHIBITED:
  ✗ Accessing customer data on personal laptop
  ✗ Viewing production logs on personal tablet
  ✗ Checking API credentials on personal phone
  ✗ Screenshots of customer information
  ✗ Installing company apps on personal phone (except Slack/email read-only)

ALLOWED ON PERSONAL DEVICES:
  ✓ Email (Slack, Gmail, Outlook) - read-only
  ✓ Slack app - read-only, no channel export
  ✓ Reading public documentation
  ✓ Calendar/scheduling

Consequences:
  • First violation: Verbal warning + retraining
  • Second violation: Written warning
  • Third violation: Potential termination


11.4 REMOTE WORK & HOME NETWORK

If working from home:
  ✓ Secure company-issued laptop (with encryption/antivirus)
  ✓ Use company VPN if accessing internal systems
  ✓ Disconnect from shared home networks if processing customer data
  ✓ Private home WiFi preferred (no public WiFi)
  ✓ Lock devices when stepping away
  ✓ No family members using company laptop
  ✓ No customer data on shared printers


11.5 DEVICE DECOMMISSIONING & DISPOSAL

When device is no longer needed:

Laptop/Desktop:
  1. Back up any non-sensitive files (3-month history)
  2. Perform full-disk wipe using built-in OS tools
  3. Reinstall OS (fresh install)
  4. Physically destroy drive if encryption cannot be verified
  5. Certificate of destruction filed

Mobile Device (Company-Issued):
  1. IT performs remote MDM wipe (all data deleted)
  2. Collect device physically for storage/recycling
  3. Destroy SIM card if personal account

Criteria for Physical Destruction:
  • Devices with unencrypted storage
  • Drives showing signs of tampering
  • Devices used to process highly sensitive data

12. PASSWORD POLICY

All passwords protecting company systems and customer data must comply
with the following standards:


12.1 PASSWORD COMPLEXITY

Minimum Requirements:
  ✓ Minimum 12 characters (longer is better: 16+ recommended)
  ✓ At least 1 UPPERCASE letter (A-Z)
  ✓ At least 1 lowercase letter (a-z)
  ✓ At least 1 number (0-9)
  ✓ At least 1 special character (!@#$%^&*)

Example GOOD passwords:
  • MyCompany2024!Secure
  • Syngage#SecureAccess$2024
  • Br0ad@BlueSky!Innovat

Example BAD passwords (DO NOT USE):
  ✗ password123
  ✗ Syngage123 (company name + numbers)
  ✗ Syngage!  (company name with special char)
  ✗ Q!@#$%^&* (random characters not memorable)
  ✗ Welcome123 (dictionary word)
  ✗ 12345678abc (too predictable)

What NOT to use:
  ✗ Dictionary words (password, welcome, admin)
  ✗ Company name or employee name
  ✗ Repeating characters (11111, aaaaa)
  ✗ Sequential numbers/letters (123456, abcdef)
  ✗ Personal information (birthdate, phone number, address)
  ✗ Previously used passwords


12.2 PASSWORD MANAGEMENT

Storage:
  ✓ Store in encrypted password manager (1Password, Bitwarden, LastPass)
  ✗ NOT in browsers (Chrome, Firefox auto-save)
  ✗ NOT on paper
  ✗ NOT in email or Slack
  ✗ NOT in code repositories

Change Frequency:
  • Initial password (first login): MUST change immediately
  • Scheduled expiry: Every 90 days
  • Emergency: Change immediately if:
    - Suspected compromise
    - Employee reports loss of access
    - Security incident involving passwords
    - Contractor/vendor departure
    - Credential appears in data breach (check https://haveibeenpwned.com)

Password History:
  • Cannot reuse last 5 passwords
  • System enforces reuse prevention


12.3 MULTI-FACTOR AUTHENTICATION (MFA)

MFA is MANDATORY for:

  ALL EMPLOYEES:
    ✓ Company email/SSO login (Microsoft 365 / Google Workspace)
    ✓ Any admin or production system access
    ✓ Any cloud platform with customer data
    ✓ VPN access

  ENGINEERS:
    ✓ Supabase database console
    ✓ AWS console (production)
    ✓ Modal control plane
    ✓ Render dashboard
    ✓ GitHub (especially if pushing to main)
    ✓ Any other CI/CD system

  CISO/SECURITY:
    ✓ 1Password vault
    ✓ Datadog security dashboards
    ✓ All security tools


Acceptable MFA Methods (Ranked):

  🥇 TIER 1 - MOST SECURE:
    • Hardware security key (Yubikey, Google Titan, Microsoft Key)
    • How: Plug physical key into USB port and press button
    • Pros: Cannot be compromised by malware
    • Cons: Cost ($40-80 per key), physical device management
    • Use for: Production database access, financial systems

  🥈 TIER 2 - RECOMMENDED:
    • Time-based OTP (One-Time Password) app
    • Apps: Google Authenticator, Microsoft Authenticator, Authy, 1Password
    • How: Generate 6-digit code that changes every 30 seconds
    • Pros: Free, built into most password managers, standard across industry
    • Cons: Can be compromised if phone compromised
    • Use for: All mandatory MFA (default choice)

  🥉 TIER 3 - ACCEPTABLE BUT NOT PREFERRED:
    • Push notification approval
    • Apps: Microsoft Authenticator, Authy
    • How: Phone receives "Approve this login?" notification
    • Pros: Very user-friendly
    • Cons: Users may approve without thinking
    • Use for: Non-sensitive systems if necessary

  ❌ NOT ACCEPTABLE:
    • SMS (text message OTP) - vulnerable to SIM-swap attacks
    • Email-based codes - interceptable
    • Security questions - answers may be public knowledge


MFA Backup Codes:

When setting up MFA, save backup codes:
  ✓ 10-12 one-time use codes
  ✓ Store in 1Password or secure vault
  ✓ Print and store in safe (locked office)
  ✓ For emergency access if MFA device lost

Never Share:
  ✗ MFA codes with anyone
  ✗ Backup codes in email/Slack
  ✗ QR codes used during setup
  ✗ Screenshots of authenticator apps


MFA Device Loss:

If your MFA device is lost (phone, hardware key):
  1. Report to IT immediately
  2. Disable MFA on affected accounts (use backup codes)
  3. Change password
  4. Re-enable MFA with new device
  5. Notify CISO


12.4 ENFORCEMENT & MONITORING

Password Compliance:
  • Audited quarterly by CISO
  • Failed login attempts monitored (>5 attempts = locked account)
  • Accounts inactive 30+ days may require MFA re-enrollment

Violations:
  • First violation: Warning + mandatory retraining
  • Repeated violations: Performance review
  • Intentional circumvention (e.g., sharing password): Termination
